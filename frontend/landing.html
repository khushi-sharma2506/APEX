What APEX does

Two engines. One question bank.

A teacher uploads questions once. The same bank powers both the adaptive live test and the offline blueprint generator.

Adaptive Live Test

Each correct answer raises difficulty; each wrong answer lowers it. The engine draws from a 250-question pool per subject so no two students see the same paper.

Blueprint Generator

Generates a balanced university paper following the mentor's 2-3-5 mark structure. Each main question is 10 marks, drawn from a different syllabus topic.

Bulk CSV Import

Drag-and-drop a spreadsheet. The importer validates every row, reports errors, and inserts all clean rows into the normalized SQLite database in under a second.

OS Performance Metrics

A live dashboard shows LRU cache hit ratio, p95 latency, ThreadPoolExecutor usage, and eviction events — direct evidence of the Operating Systems concepts implemented.

3NF Normalized Database

Subjects → Topics (with unit numbers) → Questions → MCQ Options. A B-Tree composite index on (diff_level, topic_id) ensures sub-millisecond lookups even with 10,000+ rows.

Teacher & Student Portals

Separate views for teachers (question bank, import, blueprint) and students (adaptive exam with live timer, autosave, question palette, and a topic-wise result chart).

Flow

From question bank to adaptive exam

Step 1 — Teacher

Build the question bank

A teacher drags a CSV into the import screen. APEX validates each row — subject, topic, unit number, difficulty, marks, and MCQ options — then inserts all clean rows into the normalized SQLite database in one atomic transaction.

Step 2 — Teacher

Generate a balanced paper

The blueprint algorithm iterates through topics using Round-Robin so no unit is skipped. For each main question it fetches a 2-mark Easy MCQ, a 3-mark Medium Subjective, and a 5-mark Hard PYQ — exactly what the mentor drew on the whiteboard.

Step 3 — Student

Sit the adaptive test

The student picks a topic and clicks Start. The FastAPI server dispatches each question fetch to a ThreadPoolExecutor thread. The LRU cache serves warm questions in under 0.1 ms. Difficulty adapts after every answer.

Step 4 — Admin

Monitor OS performance live

The performance dashboard polls /cache/stats every 3 seconds showing cache hits, misses, p95 latency, and the full LRU contents list — live evidence that the OS caching and concurrency concepts are working.

OS + DBMS Evidence

Built to prove concepts, not just use them.

Every OS and DBMS concept required by the B.Tech evaluation is implemented in real, running code — not described in a slide.

ThreadPoolExecutor (OS Concurrency)
20 worker threads managed by FastAPI's asyncio event loop via run_in_executor, preventing the main thread from blocking on SQLite I/O.
LRU Cache with Mutex (OS Memory Management)
Custom Python OrderedDict LRU with threading.Lock for thread-safe page replacement. Warm questions served in <0.5 ms.
3NF Schema + B-Tree Index (DBMS)
Subjects → Topics (unit_number FK) → Questions → MCQ Options. Composite B-Tree index on (diff_level, topic_id) eliminates full-table scans.
